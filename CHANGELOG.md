# Changelog

Versioning: MAJOR = architecture change (directory/state-file mechanism) · MINOR = workflow improvement · PATCH = wording/documentation fix.

## [Unreleased]

### Added

- **New optional module: `decisions`** (`modules/decisions/`) — Architecture Decision Records under `wiki/decisions/`: one `NNNN-slug.md` per decision (Context / Options considered / Decision / Consequences), a `proposed → accepted → superseded` lifecycle with a `status` frontmatter field, a **"record decision"** trigger phrase (Claude drafts from the discussion, the human confirms the status — decisions are never promoted silently), retroactive ADRs for backfilling choices made before the vault existed, a `decision` log prefix, an `index.md` Decisions section that shows each ADR's status inline, and Lint checks (status consistency across frontmatter/body/index, stale proposals, supersession completeness). Pure schema — no scripts. The module doc explicitly separates the **two levels of "superseded"**: the core `⚠️ Superseded` blockquote revises a single claim inside any page; ADR `status: superseded` overturns a whole decision file, and the two compose (an overturned ADR's dependent pages get statement-level markers citing the successor). *(code-sync + decisions both installed)* Sync gains a hard boundary: **a code diff never edits an ADR** — code contradicting an accepted decision is reported as *decision drift* for the human to rule on, because ADRs record human choices, not code state. Patterns extracted from a second real vault instance (a design-first wiki where the documents, not the code, are the source of truth); all template text written fresh for the kit.

- **New optional module: `roadmap`** (`modules/roadmap/`) — a maintained plan at `wiki/plan.md` (template shipped): optional milestones table, phases containing checkbox stories with stable IDs (`S<phase>.<n>`, never renumbered), sizes, dependencies and acceptance criteria, and per-phase **exit conditions** treated as gates. Progress discipline: ticking a box requires a completion-evidence note (when + where the result lives); structural changes and completion calls are the human's to approve; structural/completion changes get a `plan` log prefix. Lint checks gates-vs-reality, evidence-free completions, and plan/log drift. Pure schema — no scripts. *(code-sync + roadmap both installed)* Sync may report "these commits look like story X landing" and **propose** the tick, but never restructures the plan from a diff. *(decisions + roadmap both installed)* ordering discipline: the ADR comes first, then the plan edit cites it — rationale lives in `wiki/decisions/`, not buried in a story line.

- **New optional module: `related-wikis`** (`modules/related-wikis/`) — a registry at `wiki/related-wikis.md` for sibling vaults this one's subject matter connects to (a UI vault and its API vault, a service and the platform vault it depends on): each entry names the related vault, its absolute path (or `planned, not yet initialized at <path>` if it doesn't exist yet — same spirit as a `[[red link]]`, a forward reference isn't an error), and a one-line boundary of what each side owns. Since `[[wikilinks]]` only resolve within one vault, cross-vault references use a plain-text convention instead (`→ related: <VaultName> — wiki/<page>.md`), deliberately distinct from wikilink syntax so Lint's red-link/orphan scan never confuses the two. A **"link wiki"** trigger phrase registers a new entry or promotes a `planned` one to a real path once that vault actually gets initialized, a `link` log prefix records it, and Query gains a rule to point at a related vault's territory instead of parking an unanswerable question that actually belongs there. Pure schema — no scripts, and strictly read-only in both directions: this module never merges vaults or lets one edit another's pages. *(decisions module also installed)* the choice to keep vaults separate (or later merge them) is itself exactly the kind of call the decisions module exists for — file it as an ADR and cite it from the `related-wikis.md` entry. `INIT.md` Step 0 is now a five-item checklist split across two question-tool groups (the tool's 4-option cap, not the module count, is what forces the split), and Step 1 gained a seventh interview question (open-ended, asked in chat) for naming any related vaults up front.

- **Core: `wiki/question.md`** — an open-questions parking lot, the complement of `wiki/answers/`: questions that genuinely can't be answered yet (missing information, external verification, a call only the human can make) get parked instead of evaporating with the session. The exit contract is strict: an entry leaves only when the answer has been **written into the affected wiki page(s)**, not just given in chat; parking and resolving both get a new `question` log prefix, and Lint checks for entries later work has actually answered but nobody wrote back. An empty `question.md` is the healthy state.

- **Core: maintenance hints** — a page may carry a short note naming a future trigger and the edit it requires (*"once X ships, rewrite this section"*); any edit matching the trigger executes the hint and removes it once spent. Lint checks for hints whose trigger already fired.

- **New optional module: `dashboard`** (`modules/dashboard/`) — a generated `wiki/dashboard.html` snapshot: health banner, log stats (entries by op, archived count, query→answer conversion ratio), last 10 log entries, health check (red links sorted by mention count with the existing ≥3-mention "overdue" threshold, orphan pages, open `⚠️ Superseded` markers), an interactive knowledge graph, installed-module list, and copy-to-clipboard Daily Use trigger phrases. Independent of `code-sync` — installable alone (shows a sync-status section only when code-sync is also present) or together. Everything shown is mechanically derived from files already on disk (`log.md`, `index.md`, `wiki-state.json`, wikilink text); the dashboard is a real script (`scripts/dashboard.ps1` / `dashboard.sh`, both self-contained, no shared code between them), not an LLM computation — no `claude -p` call, no token cost, runnable standalone with no Claude Code session open. The page's buttons only copy trigger phrases to the clipboard (with a `document.execCommand('copy')` fallback for browsers that block the async Clipboard API on `file://` pages) — there is no backend and nothing executes from the page itself; the human still pastes the phrase into a Claude Code chat. *(code-sync + dashboard both installed)* `sync.ps1`/`sync.sh` now calls the dashboard script automatically after a successful sync (best-effort — a dashboard failure warns but never fails the sync). `INIT.md` Step 0 is now a two-item module checklist (`code-sync`, `dashboard`) instead of a single yes/no, and gained a dashboard dry-run to its Step 3 self-check.

- **Dashboard knowledge graph** — an Obsidian-style force-directed graph of every wiki page and the `[[wikilinks]]` between them that resolve to a real page (red links are excluded — they're already surfaced in the Health check card). Nodes are colored by their top-level `wiki/` subfolder and sized by inbound-link count; drag nodes, pan the background, scroll to zoom, double-click to reset. Rendered with a small vanilla-JS canvas force simulation embedded in `dashboard.template.html` — no external charting/graph library, keeping the page self-contained and offline-usable. `dashboard.ps1`/`dashboard.sh` compute only the node/edge *data* (id, label, folder-derived group, degree) deterministically from the same wikilink scan already used for red-link/orphan detection — the live layout itself is client-side physics, not something the scripts compute or need to keep in sync with each other. File enumeration in both scripts is now sorted (previously relied on OS-dependent directory-walk order), so the two scripts produce identical node/edge data for the same vault state. The force simulation had an uncapped-repulsion bug that caused visible flickering on densely-linked vaults (two nodes drifting close together would spike the repulsion force toward infinity, then overshoot and repeat); fixed with a minimum-distance floor, a per-frame velocity clamp, and an alpha "cooling" factor so the layout settles instead of jittering forever, reheating only when a node is dragged — caught via user report on a real 53-page vault after the graph's initial synthetic testing (small/sparse fixtures) hadn't hit the dense-cluster case that triggers it. That same real vault (330 wikilink edges across only 53 pages — much denser than the synthetic test fixtures) then exposed a second issue once the flicker was gone: the fixed repulsion constant was tuned for a sparse graph and couldn't counteract that many springs, so everything collapsed into one overlapping clump. Replaced the fixed repulsion/rest-length constants with Fruchterman-Reingold-style scaling (an "ideal distance" `K` derived from canvas area and node count, so both repulsion and spring rest-length scale with how dense the graph actually is), added a short synchronous warm-up pass before the first paint, and an auto-fit-to-view on load and on double-click (previously double-click reset to a fixed scale/center that didn't account for the graph's actual settled size). Labels are now always drawn regardless of zoom level (previously hidden below a fixed zoom threshold, which meant a real graph's typical auto-fit zoom showed no labels at all). Also added hover highlighting (missing from the initial implementation): hovering a node now highlights it and its direct connections in the accent color and dims everything else, matching Obsidian's graph view — previously hover did nothing at all.

- **New optional module: `tickets`** (`modules/tickets/`) — a lightweight day-to-day kanban layer, a different altitude from `roadmap`'s phases/stories and `decisions`'s ADRs: `wiki/tickets/` holds one file per ticket (`{{TICKET_PREFIX}}-NNNN-slug.md`, numbered in creation order, never reused), each with a `status` frontmatter field (`backlog | in-development | in-review | resolved`) and a Status/Summary/Notes body skeleton; `wiki/board.md` is a single file formatted for Obsidian's community **Kanban** plugin (four `##` columns, cards as `[[wikilink|alias]]` list items) — a soft dependency, since the file still reads fine as plain markdown without the plugin installed. **"create ticket \<title\>"** files a new ticket and adds its card to Backlog; **"move ticket \<id\> to \<column\>"** updates both the frontmatter and the board in one edit. Deliberately looser than decisions/roadmap: movement is mechanical on the human's word for every column including Resolved, no separate approval gate, since tickets are operational rather than architectural commitments. `index.md` gains a `## Tickets` section that's a single pointer (`see [[board]]`) rather than a per-ticket listing — `board.md` is already the current-state index, so duplicating it would just be a second place to go stale. A `ticket` log prefix and a Lint check (frontmatter `status` = Status line = the card's column on the board, three-way; every ticket has exactly one card, no orphans either direction) round it out. Pure schema — no scripts. *(roadmap also installed)* independent, cross-referenced in plain text (`implements S2.3` / `tracked as {{TICKET_PREFIX}}-0007`) since individual plan stories aren't their own files to wikilink. *(decisions also installed)* a ticket downstream of a choice can cite its ADR directly (`per [[NNNN-slug]]`). `dashboard.ps1`/`dashboard.sh` detect the module (`wiki/tickets/` marker) for the Installed-modules card and gain a `create ticket` Daily Use button; `core/wiki/log.md`'s prefix line and `INIT.md`'s Step 0 checklist (now six modules, still fits two four-option question-tool groups without a third), Step 1 interview (an eighth question for `{{TICKET_PREFIX}}`), Step 2 assembly/README template, Step 3 self-check, and Step 5 handoff all extended to match, same pattern each prior module followed.

- **New optional module: `flows`** (`modules/flows/`) — end-to-end process/runtime flow diagrams under `wiki/flows/`: one topic-keyed page per process (no numbering, unlike `decisions`/`tickets` — a flow is identified by what it documents, not when it was filed), each a Mermaid `flowchart` (start point, every step in execution order, every decision branch and where it goes, where it ends) plus a step-by-step what/why/next explanation written to be legible to both a non-technical reader and someone technical. Same "don't fill a gap with a guess" discipline as the rest of the wiki, made explicit for this module: anything the source doesn't establish clearly gets flagged **不明确 / Unclear** in its own section rather than a plausible-sounding invented branch. A **"flow it" / "画流程图"** trigger phrase (bilingual, same precedent as core's "archive this" / "归档") means "apply this module's full spec to `<topic>` without re-stating it" — the origin was a real vault where the human had a detailed one-off prompt for exactly this shape of output and wanted it reusable across topics without re-pasting it each time; this module *is* that prompt, generalized and kept current in the schema instead. A flow page owns the step-by-step description of the process it covers; the entity pages it touches get a one-line pointer back rather than a duplicate prose walk-through, so the two can't quietly drift apart. `index.md` gains a `## Flows` section (one line per page, no status annotation needed — a flow either exists or doesn't, unlike an ADR's lifecycle), a `flow` log prefix joins the set, and Lint gains two checks: flow-entity cross-link consistency, and (*code-sync also installed*) flagging a flow page whose `synced_at_sha` is older than a `code_refs` file's last real change with higher priority than an ordinary stale claim, since a stale flow diagram is a control-flow correctness bug, not just an outdated fact. Pure schema — no scripts. *(code-sync also installed)* Sync never invents a flow page from a diff alone, same as any other page — it updates an existing one or flags that a new one looks warranted. *(decisions also installed)* a flow can cite the ADR behind a branch that exists because of an architectural choice (`per [[NNNN-slug]]`). `dashboard.ps1`/`dashboard.sh` detect the module (`wiki/flows/` marker) for the Installed-modules card and gain a `flow it` Daily Use button; `core/wiki/log.md`'s prefix line, `INIT.md`'s Step 0 checklist (now seven modules, split 4+3 across the two question-tool groups — no new Step 1 interview question needed, since flows has no vault-specific placeholder to fill), Step 2 directory scaffold/assembly/README template, and Step 5 handoff all extended to match, same pattern each prior module followed.

### Changed

- Roadmap story acceptance criteria (`modules/roadmap/CLAUDE.roadmap.md`, `modules/roadmap/wiki/plan.md`) are now given/when/then, explicitly required to cover bad paths as well as the happy path — previously a story just needed prose stating "the acceptance criterion that decides done," with no shape, which left failure behavior to be inferred rather than stated. A story can carry more than one given/when/then line but never zero.
- ADR body skeleton (`modules/decisions/CLAUDE.decisions.md`) gained a **Constraints** field between Decision and Consequences: what the decision puts off-limits going forward (a system nothing may call directly, a pattern now forbidden), distinct from Consequences' downstream fallout. Written as `none` explicitly when a decision doesn't restrict anything, so an empty section reads as a deliberate answer rather than an oversight.
- Core page-format rules (`core/CLAUDE.core.md`) gained an explicit **don't fill a gap with a guess** rule: when source material doesn't state something, the page leaves it as a red link / explicit unknown / `question.md` entry rather than a plausible-sounding uncited claim — naming the failure mode directly rather than relying only on the citation convention to prevent it implicitly.
- `INIT.md` Step 0 is now a **four**-item module checklist (`code-sync`, `dashboard`, `decisions`, `roadmap`) — exactly filling the question tool's 4-option limit, noted in the step so a future fifth module knows to split into two rounds. Step 2 gained assembly/instantiation instructions for the two new modules (plus `question.md` joining the core tree), and Step 5's handoff gained module-matched next-step notes (backfill the big decisions already made; seed `plan.md` by dictation or ingest). `wiki/decisions/` is scaffolded with a `.gitkeep` rather than empty — git doesn't track empty directories, so without it the module's on-disk marker (which the dashboard detects) would vanish from any fresh clone until the first ADR landed.
- The dashboard module learned about the new modules: `dashboard.ps1`/`dashboard.sh` now detect `decisions` (presence of `wiki/decisions/`) and `roadmap` (presence of `wiki/plan.md`) for the Installed-modules card, and show a `record decision` Daily Use button when decisions is installed. Log-stat op counting needed no change — both scripts already count whatever ops actually appear in `log.md` rather than a fixed list. The orphan check now also excludes `question.md` (a hub file every new vault ships with zero inbound links — previously every fresh vault would have opened on a permanent false-positive orphan and a yellow banner).
- `⚠️ Superseded` blockquotes now have a defined lifecycle (core page-format rules): they are **history annotations, not open tasks** — the claim above one is already current, so its presence never counts as an unresolved problem; Lint may propose pruning one that no longer adds context, with human approval. The dashboard follows suit: the marker count is still shown but is informational — it no longer degrades the health banner (previously a single correctly-recorded supersession turned the banner yellow forever, which the decisions module's requirement that overturned ADRs leave statement-level markers would have made permanent by design).
- `modules/code-sync/CLAUDE.code-sync.md` gained an explicit "log.md — bootstrap / sync / config prefixes" section matching the pattern the new modules established, and core's `{{CODE_SYNC_LOG_PREFIXES}}` assembly comment now includes `config` — previously the `config |` prefix that "set commit noise" actually writes never entered the assembled schema's documented prefix set.
- `README.md`'s design principles gained a fourth: **descriptive pages follow the source; prescriptive pages follow the human** — `wiki/decisions/` and `wiki/plan.md` record choices and commitments, so no workflow may rewrite them off source material alone; code diverging from a decision is drift to report, not a page to auto-correct.

- Lint (`core/CLAUDE.core.md`) gained a `log.md` archiving check: entries whose content is fully reflected elsewhere can be tagged `⚠️ Archived <date>` on their header line — non-destructive (nothing is deleted or rewritten) and reversible, unlike an earlier compaction design considered and rejected during development (collapsing old entries into rewritten one-line summaries) once a worked example showed it could silently discard process/methodology detail no wiki page would otherwise capture. `log.md`'s own section gained a matching reading rule: grep headers instead of reading start to finish, skip the body of `Archived`-tagged entries by default. Surfaced by real usage of a vault built from this kit, where `log.md` had grown past 140 lines with no defined way to keep routine reads cheap. Actual size-reduction (compaction/summarization of long-archived entries) is deliberately left undesigned — revisit only if archiving alone proves insufficient.

## [0.1.0] - 2026-07-19

### Changed

- Quickstart trigger phrase shortened to a copyable `init vault` block; added a root-level placeholder `CLAUDE.md` that points fresh sessions at `INIT.md` (auto-loaded by Claude Code, so the short phrase resolves deterministically). It's overwritten by the assembled vault `CLAUDE.md` during Init Step 2.

- `INIT.md` Step 2 now deletes the kit's own scaffolding (`core/`, `modules/`, `examples/`, `INIT.md`, `IDEA.md`, `README.md`, `CHANGELOG.md`, and a cloned kit's `.git/`) before the vault's initial commit — previously this was left for the human to clean up manually, and the "self-contained vault" promise depended on them remembering to.
- `INIT.md` interview now runs in **mixed mode**: closed-choice questions (module selection, entity categories, language convention, sync-noise rules, tracked branch) go through the environment's interactive question tool (option cards — `AskUserQuestion` in Claude Code) when one is available; open-ended answers (project description, repo path — asked with an OS-appropriate example path) stay in chat; and the tracked branch is picked from a real `git branch` listing instead of typed by hand. Falls back to fully conversational when no question tool exists, so the interview still works outside Claude Code.
- Bootstrap pacing reworked (`modules/code-sync/CLAUDE.code-sync.md`): instead of confirming with the human between every batch (a rubber-stamp in practice — humans type "continue" without reviewing), the human is needed at exactly two points — the batch plan, and a batch-1 style spot-check — after which the remaining batches run straight through with one-line progress notes, stopping only on genuine anomalies (contradictions with existing pages, unplanned oversized areas, context pressure). Each batch still commits, so batch boundaries stay clean resume points; either mode can be switched at any boundary.
- `README.md` gained a **Day-2 usage** section (`run sync`, `set commit noise`, Ingest, Query, `run lint`) — previously the README stopped at "run Bootstrap" and never said how a running vault is actually operated day to day.
- `modules/code-sync/` gained a **"set commit noise"** trigger phrase: Claude scans the tracked repo's recent `git log`, presents the noise patterns it actually observed (with frequencies) as a multi-select, and writes the chosen rules back into the Sync triage line plus a `config |` log entry. Closes the loop the Init interview deliberately leaves open ("don't know yet — refine after the first few real Syncs" now has a defined refine action).
- Ingest (`core/CLAUDE.core.md`) gained a second entry point: give a filesystem path in chat and Claude verifies + **copies** the file into `raw/` itself (copy, never move — the original is untouched), renaming information-free filenames to `<content-date>_<slug>` while keeping meaningful ones, and recording `raw_file:` + `original_path:` provenance in the source page. Attachments pasted directly into chat can't be archived (no file on disk to copy) — the defined fallback is ask-for-a-path, then a flagged summary-only ingest (`raw_file: none`). Also clarified that `raw/`'s "read-only" means append-only: adding files is normal, modifying or deleting existing ones is not.
- `INIT.md` gained a Step 4 — **Register the vault in the user-global `~/.claude/CLAUDE.md`** (with human confirmation, since it edits a file outside the vault). Without this pointer, sessions working in the project repo never think to consult the wiki, and it silently goes unused. Old Step 4 (Handoff) is now Step 5; the self-check gained a matching "no kit files remain, no kit git history" check.
- `IDEA.md` gained a principle on Bootstrap's cost economics: the structure/module passes are the most expensive thing the kit does, and only pay for themselves if the wiki is queried repeatedly afterward — a vault built once and abandoned is a net loss.
- Query (`core/CLAUDE.core.md`) gained explicit offer/don't-offer criteria for filing to `wiki/answers/` (previously just "real synthesis and reuse value," which left the judgment call to drift between sessions), plus an **"archive this" / "归档"** on-demand trigger phrase so the human isn't limited to Claude's own offer — invoking it also folds the finding back into every entity page it touches, not just the answers file, closing a gap where manual archiving previously needed a separate follow-up ask to update the source pages. `log.md` gained a matching `answer |` prefix. `README.md`'s Query bullet documents the new phrase.
- `INIT.md` Step 2 no longer deletes `README.md` as scaffolding — it now **overwrites it with a short, vault-specific one** (project description + Day-2 phrases matching the modules actually installed), so a human landing on the repo without Claude Code open still has something better than `CLAUDE.md` to read. Previously the vault was left with either the kit's own README (which describes the kit, not the vault, and points at directories that no longer exist post-Init) or nothing. Step 3 self-check gained a matching "README describes the vault, not the kit" verification.
- `README.md` gained a **Prerequisites** section, previously missing entirely — Claude Code (on a plan/account that can run it), `git` (every vault, not just code-sync, gets `git init`'d), Obsidian (optional but the wiki's `[[wikilink]]` format is written specifically for it), and PowerShell/bash (optional, only for headless `scripts/sync.ps1`/`sync.sh`).
- `README.md` gained an illustrative graph-view image (`kit-assets/graph-view-example.svg`) showing what a filled-in vault looks like in Obsidian — generated fresh with generic placeholder labels rather than a screenshot of any real vault, to keep the kit free of real project specifics. `kit-assets/` is kit-only scaffolding, so `INIT.md`'s deletion list and self-check gained it alongside `core/`/`modules/`/`examples/`.

- "Day-2 usage" heading simplified, then settled on **"Daily Use"** (not "Usage") — matches the original wording from the source vault this kit was extracted from, in `README.md`'s own section and in the vault-README template `INIT.md` Step 2 assembles for every future vault.

Extracted from a private single-project vault (a data-engineering wiki; anonymized here as `chain-metrics`) after it completed one full real-usage cycle (5 real Queries, 5 real Ingests, 1 Sync, 1 Lint — see that project's `PLAN.md` §2/§9 for the extraction evidence trail). Extraction was started deliberately before the originally-planned gate (≥5 Sync runs, 2-week `CLAUDE.md` stability window) finished, by explicit decision of the vault's maintainer — noted here rather than glossed over, since it means this kit's `code-sync` module has only been battle-tested against one real Sync so far, not the five originally intended.

Tagged `v0.1.0` ahead of the acceptance test (§6 in the source project's `PLAN.md`: initializing a genuinely different kind of vault — non-code, e.g. a book or a research topic — purely from `INIT.md`, with no prior context), by explicit decision of the maintainer — noted here rather than glossed over. Until that test passes, treat every file here as usable-but-unproven outside the single data-engineering instance (`examples/chain-metrics/`) it came from.
